# Managed Runtime API Responsiveness Plan

## Problem and approach

Multiple Streamliner-managed SDK sessions can drive the local API into file-store and SSE write amplification because each sanitized SDK event currently patches runtime metadata immediately and broadcasts a full session upsert. The implementation will keep the session registry as the canonical bounded projection while adding a same-process coalescing layer for routine managed progress, prompt flush semantics for state/evidence that builders rely on, and lighter live-session delivery so connected dashboards do not keep polling the list endpoint while SSE is healthy.

## Work items

1. `lite:managed-runtime-api-responsiveness:work:managed-runtime-coalescer` - Add a managed-runtime patch coalescer used by managed launch/resume callbacks. Routine progress plus repeated routine lifecycle assertions should batch per registry row on a short throttle window, while launch startup, started metadata, first entry into a lifecycle state, lifecycle classification changes, terminal lifecycle states, PR/completion evidence, other evidence, failures, interrupts, takeover, cleanup, and builder-input transitions flush promptly. The coalescer must always merge progress and lifecycle callbacks from the same SDK event tick into one registry write, including the canonical `tool.execution_start` progress-plus-`running` case, and must expose a flush/dispose path for tests and terminal/error paths.
2. `lite:managed-runtime-api-responsiveness:work:event-stream-chatter` - Reduce event-stream and browser chatter. Make `/api/sessions/events` query-aware for both connection snapshots and live events so clients scoped to a workstream/node do not receive irrelevant full-session upserts. Add a compact runtime-update event if practical for runtime-only changes; if not, the responsiveness win must come from query filtering plus polling suspension while preserving full `session.upserted` as the canonical update shape. Update `useSessionRegistryList` to apply live payloads directly, fetch or require a full upsert for unknown compact-event session ids, and suspend interval/focus polling only while SSE is live and heartbeats or other events keep the stream fresh.
3. `lite:managed-runtime-api-responsiveness:work:responsiveness-coverage` - Add targeted coverage showing bounded registry writes under managed SDK event bursts, prompt flush for important transitions/PR evidence/completion evidence/failures, exactly one runtime patch for a `tool.execution_start` event that produces both progress and lifecycle callbacks, reduced SSE payload/chatter for filtered streams or compact runtime updates, unknown compact-event reconciliation if compact events are added, and no redundant list polling while a live EventSource is connected. Extend existing tests where appropriate: `src/server/managed-sdk-runner.test.ts`, `src/server/node-launch.test.ts`, `src/session-registry/file-store.test.ts`, `src/server/app.test.ts`, and `src/App.test.tsx`; add new module tests only for genuinely new helpers such as a coalescer. Run the repo's normal lint/build/test gates after implementation.

## Key decisions and constraints

- The registry remains canonical and bounded; raw SDK events stay excluded. Stored progress continues through the existing runtime sanitizer and retention limits.
- Routine lifecycle reassertions such as repeated `running` or `idle` updates may be coalesced with progress. First entry into a state, active-to-terminal changes, terminal-to-cleanup transitions, PR/completion evidence, failures, interrupts, takeover, cleanup, and builder-input transitions must not wait behind the throttle. If a single SDK event yields both progress and a flush-worthy lifecycle change, the merged write flushes immediately.
- The coalescer lifecycle is bound to the registry row and launch claim. Claim release, terminal ownership transfer, cleanup, or managed-run failure must flush or intentionally drop pending row-local patches before disposal so late SDK callbacks cannot resurrect terminal-owned or cleaned-up runtime metadata, and a later launch cannot reuse a stale queue.
- Existing full `session.upserted` semantics should remain available for non-runtime changes and initial snapshots. Any compact event must be an additive internal SSE event consumed by the current client, not a breaking API replacement. If the compact runtime-update event is not implemented, the client must continue to handle full `session.upserted` payloads as the canonical update shape and tests must prove query-aware filtering plus polling suspension provide the chatter reduction.
- SSE polling suspension depends on stream liveness. The client may pause interval/focus refetch while EventSource is live, but should resume fallback polling on connection errors or bounded heartbeat/event staleness so a silently dead stream cannot freeze the session list.
- UI changes are behavioral rather than visual; screenshots are not expected unless implementation changes rendered layout.
- Out of scope: child-process supervision, remote workers, and the managed-session console.
